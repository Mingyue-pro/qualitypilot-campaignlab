# CampaignLab 在 QualityPilot 中的项目配置清单

> 本清单严格对应 QualityPilot 当前结构：先创建项目、配置项目知识，再创建一条待测试需求进入 Understand。它不是简单的文件目录。

## 一、创建项目

项目名称：`CampaignLab`

项目描述：

```text
CampaignLab 是一个使用合成业务、合成用户画像和模拟渠道构建的营销流程被测系统。
它包含 CDP 客群管理、MDP 营销计划画布和执行监控，用于验证 QualityPilot
对新需求的理解、风险分析、测试设计、API 执行、缺陷发现与回归闭环。
CampaignLab 不复刻原公司系统，也不包含真实客户数据。
```

版本边界：

- 当前系统基线：`V1.0`，以代码、实际测试结果、OpenAPI 和真实数据库结构为准。
- 本次待测试需求：`V1.1 单计划用户日触达频控`，尚未实现。
- 历史 Bug 是合成知识，不是真实公司缺陷。

### 基本信息建议正文

```text
业务范围：CDP 客群管理、MDP 营销计划画布、营销执行监控。
前端：Vue 3 + TypeScript + Vite。
后端：Java 25 + Spring Boot 4.1.1。
数据库：本地 Docker MySQL 8.4；H2 仅用于自动化测试。
渠道：短信、外呼、发券均为模拟渠道，不产生真实触达。
当前版本：V1.0。待测试版本：V1.1。
```

### 产品文档

现有 V1.0 PRD 和业务规则混有审批、暂停、互斥、旧频控等尚未完整实现的设计，不能直接标记为“当前事实”。正式导入前应校准为当前 V1.0 基线，或标记为“历史目标草稿”。

V1.1 `PRD.md` **不要放进项目级产品文档并当作既有知识**。它应放在具体需求的 Understand 输入中，避免将新需求误认为旧系统能力。

### 数据库知识

优先输入实际 Schema，而不是只给人工 ER 图：

- `src/main/resources/db/migration/V1__initial_schema.sql`
- `src/main/resources/db/migration/V2__marketing_plan_canvas.sql`
- `src/main/resources/db/migration/V3__execution_trace.sql`
- `docs/DATA_DICTIONARY.md` 作为业务解释补充

QualityPilot 应从 Schema 确定表、字段、主外键和约束，再生成 ER 图、业务解释和待确认问题；人工确认后发布。MVP 只读取本地/测试库元数据，不读取生产业务数据，不执行修改 SQL。

### 接口文档

- 主合同：`openapi/openapi.json`
- 人工说明：`docs/API_CONTRACT.md`
- 错误断言参考：`docs/ERROR_CODES.md`

当前 OpenAPI 描述 V1.0 已实现接口。V1.1 尚未实现时，不提前把频控字段写进当前合同。

### 历史 Bug

每条 Bug 至少携带：Bug ID、影响版本、状态、前置条件、复现步骤、预期、实际、风险标签及 `synthetic=true`。

- `fixed` 表示合成历史版本中已修复，不代表未来能力已经实现。
- 历史 Bug 用于风险联想和回归建议，不能直接作为当前缺陷结论。
- BUG-002 的旧频控描述不是 V1.1 最终规则。

### 暂时留空的栏目

- 历史测试用例：Java 自动化测试是代码证据，不等同于已治理的历史业务用例。
- 测试复盘：`INTERVIEW_REVIEW.md` 是个人学习材料，不是 CampaignLab 测试知识。

### 外部系统待补说明

后续文档至少说明模拟 Doris、短信、外呼、发券系统各自的输入、输出、失败类型、幂等边界和数据责任方，并明确均未连接真实系统。

## 三、创建 V1.1 测试需求

需求名称：`V1.1 单计划用户日触达频控`

需求描述：

```text
同一营销计划内，同一用户在 Asia/Shanghai 自然日内达到触达次数上限后，
后续再次执行仍允许系统创建执行与节点轨迹，但必须被频控拦截，不能再次调用渠道，
也不能新增该用户的渠道回执。统计必须跨该计划当天的所有执行批次。
```

## 四、Understand 的三个必填输入

### 1. PRD

主输入只使用 `requirements/v1.1/PRD.md`。

下列内容作为本需求补充附件，不是 V1.0 旧知识：

- `BUSINESS_RULES.md`
- `CHANGE_IMPACT.md`
- `ACCEPTANCE_CRITERIA.md`
- `TEST_DATA.md`

### 2. 测试人员初始理解

必须由测试人员看完 PRD 后先独立填写，不能让 QualityPilot 先给标准答案。至少回答：

1. 谁会在什么条件下被拦截？
2. “同一计划、同一用户、同一自然日”怎样识别？
3. 成功和失败的渠道调用是否都计数？
4. 第二次被拦截后，执行批次、节点轨迹、渠道回执分别怎样变化？
5. 哪些边界还需要产品确认？

### 3. 需求存在原因

| 字段 | 建议内容 |
|---|---|
| 原因 | 同一计划可能被多次执行，当前缺少跨执行批次的用户日触达保护 |
| 目标 | 限制单计划对单用户在一个上海自然日内的渠道调用次数 |
| 业务证据 | 重复触达损害用户体验，并增加短信、外呼或权益成本 |
| 必要性 | 只统计单次执行批次无法覆盖同日重复执行 |
| 不做的影响 | 用户可能被同一计划重复触达，监控数据也与频控规则不一致 |
| 确认人 | 实际扮演产品负责人的人员填写 |
| 确认状态 | 人工确认后才能改为已确认，Agent 不能自动确认 |

## 五、Understand 的可选输入

- OpenAPI：V1.0 `openapi/openapi.json`，作为变更前接口基线。
- 目标测试环境：`CampaignLab Local`。
- 补充材料：V1.1 业务规则、影响分析、验收标准和测试数据。

必须保留版本差异：V1.0 OpenAPI 是当前事实，V1.1 PRD 是待实现变化。

## 六、Agent 不可见的评测资料

以下内容只由评测程序或验收人员保管：

- 受控缺陷的具体代码位置和错误实现方式；
- “只统计当前 `run_id`”等直接揭示根因的提示；
- 隐藏 Golden Case、最终 Oracle 和评分脚本；
- 修复补丁、正确实现代码；
- 期望 QualityPilot 输出的缺陷标题或完整答案。

需求可以说明正确业务规则，但不能提前告诉 Agent 被测代码错在哪里。

## 七、不要导入

- `target/`、`node_modules/`、`dist/`、缓存和构建日志；
- `.env`、数据库密码、API Key 和真实凭据；
- 真实用户、手机号、公司客户资料；
- `docs/INTERVIEW_REVIEW.md`；
- QualityPilot 自身 PRD、架构和 Agent 文档；
- CampaignLab 全量源码（MVP 项目知识不靠源码替代合同和业务文档）。

## 八、当前 QualityPilot 的真实能力边界

当前前端能创建项目、创建需求，并在页面状态中配置知识栏目；但不能因页面存在，就声称真实文件上传、解析、持久化、RAG 发布、OpenAPI 执行和数据库连接均已完成。

- 本清单定义正确的目标配置。
- 页面填写成功不等于资料已持久化并可被 Agent 检索。
- 后续必须用代码和端到端测试证明上传、解析、确认、检索与执行链路。

## 九、接入验收条件

- [ ] 创建 CampaignLab 项目，明确 V1.0 基线与 V1.1 待测试需求。
- [ ] 九类知识逐项处理；缺失栏目留空，不用无关材料凑数。
- [ ] 产品文档不再把未实现能力描述成当前事实。
- [ ] OpenAPI、Schema 和历史 Bug 带版本与状态。
- [ ] 单独创建 V1.1 需求，没有将它混入 V1.0 既有知识。
- [ ] 测试人员先提交初始理解，再让 Agent 对比分析。
- [ ] 需求存在原因经过人工确认。
- [ ] Agent 能区分当前事实、待实现需求、历史参考和隐藏答案。
- [ ] Agent 无法检索受控缺陷根因、Golden Case 和评分脚本。
- [ ] 所有“已接入”结论都有持久化、检索或执行证据。

正式接入前还需：

1. 校准 V1.0 产品文档和业务规则；
2. 更新测试环境文档，补充模拟外部系统说明；
3. 历史测试用例和测试复盘保持为空，等真实产出后再建立知识。
