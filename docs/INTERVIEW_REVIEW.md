> 用途：每完成一个开发步骤，就在这里记录业务目标、设计选择、实现链路、测试证据和面试表达。  
> 口径：只把已经运行并验证的内容说成“已实现”；未完成能力统一说成“设计中”或“下一阶段”。

## 一分钟项目介绍

CampaignLab 是我为了验证 QualityPilot 测试智能体而设计的合成营销平台。它参考了我在 CDP 客群圈选和 MDP 营销场景中的经验，但没有复刻原公司的系统，也不使用真实客户数据。

平台的目标不是建设一个生产级营销中台，而是提供一个业务规则足够完整、接口可执行、结果可验证、缺陷可复现的被测系统。V1.0 的完整目标链路是：客群圈选、营销计划配置、审批、执行过滤、模拟触达和监控。目前已经完成第一段客群链路：从 H2 模拟的 Doris 用户画像表按标签圈选用户，保存不可变客群快照，生成新版本并发布给未来的营销计划使用。

技术上，CampaignLab 是独立的 Java Spring Boot 应用，QualityPilot 是 Python 应用，两者未来通过 HTTP/OpenAPI 连接。这个边界让我既能验证传统接口和业务规则，也能验证 AI 是否正确理解 PRD、历史 Bug、接口合同和执行证据。

## 第一步：确定被测系统定位

### 为什么做

QualityPilot 如果只有 AI 分析页面，没有真实可执行的被测系统，就无法完成“理解需求—设计用例—调用 API—判断结果—形成缺陷证据”的完整验证。因此需要一个规模可控，但有真实业务状态、数据库和接口的营销系统。

### 关键决策

- CampaignLab 是合成营销平台，不是原公司 MDP 的复制品。
- 只借鉴通用业务经验：客群、计划、审批、过滤、触达、监控。
- 所有用户、渠道结果和历史 Bug 都是合成数据。
- CampaignLab 放在同一父仓库的独立 `campaignlab/` 文件夹中，不放进 Python 包，也不建立单独 Git 仓库。

### 面试表达

AI 测试开发方向：

> 我没有只做一个生成测试用例的 Demo，而是补建了一个可控的营销被测系统。这样 Agent 的输出可以落到真实 HTTP 调用、数据库状态和回归结果上，能够验证它是否真的发现问题。

AI 产品经理方向：

> 我先定义了产品验证边界：CampaignLab 不是第二个主产品，而是 QualityPilot 的验证基础设施。因此我控制它的范围，只实现能产生高价值测试证据的业务链路。

## 第二步：决定 CDP 与 MDP 的边界

### 业务问题

真实经验中，CDP 负责圈选客群，MDP 直接使用已经形成的客群进行营销。如果在练习项目中拆成两个完整系统，开发成本会很高；如果完全省略圈选，营销计划又缺少可信输入。

### 设计结果

在同一个 CampaignLab 应用中放置两个逻辑模块：

```text
CDP 客群中心
标签条件 → 查询模拟 Doris → 预览成员 → 保存版本 → 发布版本

MDP 营销中心（下一阶段）
选择已发布客群版本 → 配置流程 → 审批 → 执行 → 模拟触达
```

CDP 与 MDP 不拆成两个服务，但责任仍然分开。MDP 不能临时重新计算客群，而要绑定明确的已发布版本，保证审批时看到的人群与执行时使用的人群一致。

### 面试追问：为什么要做客群快照

用户标签会变化。如果营销计划保存的只是筛选表达式，那么审批之后再次执行查询，成员可能已经变化，结果难以审计。保存不可变快照后，系统可以回答“某次营销到底面向了哪些用户”。需要最新人群时，不修改旧版本，而是刷新生成 V2。

## 第三步：建立可重复的合成用户数据

### 已实现内容

- 建立 `doris_user_profile` H2 表模拟 Doris 用户画像宽表。
- 准备 6 条固定合成用户数据。
- 支持 `city`、`memberLevel`、`newUser`、`riskLevel`、`marketingAllowed` 等白名单字段。
- 使用 `UserProfileSource` 接口隔离数据源，当前由 `H2DorisProfileSource` 实现。

### 为什么不直接连接真实 Doris

V1.0 需要的是稳定、可重置和可验证的测试数据。真实 Doris 会增加环境、权限和数据治理成本，但不会提升当前闭环的核心证明力。通过数据源接口保留未来替换 JDBC 实现的可能，同时对外准确描述为“H2 模拟 Doris”，避免技术包装。

### 代码链路

```text
页面标签条件
  → AudienceController 接收 HTTP 请求
  → AudienceService 校验角色、字段和业务规则
  → UserProfileSource 查询用户画像
  → H2DorisProfileSource 使用 JPA Criteria 组合条件
  → 返回匹配用户并保存客群成员快照
```

职责可以这样解释：

- Controller：处理 HTTP 输入输出和接口流转。
- Service：执行权限校验和客群业务逻辑。
- Repository/Data Source：读取或保存数据库记录，不决定业务规则。
- Database：保存当前用户画像、客群版本和成员快照。

## 第四步：实现客群版本和发布

### 核心规则

1. 创建客群时生成 V1 和成员快照。
2. 刷新客群时根据当前画像重新计算，生成 V2，不覆盖 V1。
3. 发布版本后，该版本可以被未来的营销计划选择。
4. 已发布版本的成员快照不能随用户画像变化而改变。

### 典型面试测试场景

假设 V1 发布时 U001 是 VIP，因此属于客群。之后 U001 变成普通会员：

- V1 仍包含 U001，因为它是已经发布的历史快照；
- 重新刷新生成的 V2 不再包含 U001；
- 已绑定 V1 的营销计划仍然使用 V1，不能悄悄改用 V2。

这条用例同时验证了版本不可变、数据可追溯以及计划输入稳定性。

## 第五步：实现接口校验和自动化测试

### 已验证的客群场景

1. `上海 + VIP + 新用户` 只匹配 U001。
2. 请求使用非白名单标签时，返回 `INVALID_AUDIENCE_RULE`。
3. 非运营角色不能创建客群。
4. 刷新生成 V2，同时 V1 仍然存在。

### 测试方法

测试从 HTTP 层发起请求，穿过 Controller、Service、Repository 并使用 H2 数据库，因此验证的不是一个孤立函数，而是一条可运行的业务链路。

### 如何判断“行为正确”

不能只看 HTTP 200，需要同时检查：

- 响应状态和错误码是否符合 OpenAPI/接口合同；
- 返回的成员数量和成员 ID 是否符合固定测试数据；
- 失败请求是否没有产生不应有的数据库变更；
- 新版本是否创建，旧版本是否仍然可查询；
- 发布状态是否只作用于指定版本。

### 面试表达

> 我把业务规则转成了可重复的 HTTP 集成测试。例如非法标签不仅要返回错误，还要确保不会保存错误客群；刷新客群不仅要得到新成员，还要验证旧版本没有被覆盖。这样测试关注的是状态变化和副作用，而不只是接口返回值。

## 历史 Bug 知识库怎么讲

CampaignLab 准备了合成的历史 Bug 知识库，例如标签条件取反、并发下频控绕过、对照组被错误触达、监控统计重复。这些 Bug 不是声称来自原公司的真实事故，而是根据营销系统的典型风险设计的测试资产。

QualityPilot 后续可以使用这些资料：

1. 从新需求和历史 Bug 中识别高风险规则；
2. 生成带依据的测试场景；
3. 调用 CampaignLab API 执行用例；
4. 根据响应、数据库状态和执行记录判断缺陷；
5. 把已确认缺陷沉淀回项目知识库，支持以后回归。

## 常见追问与回答

### 这是你原公司的系统吗？

不是。它只参考通用的 CDP/MDP 工作经验，业务、数据、Bug 和渠道全部是合成的，目的是构造一个合法、可控、可公开演示的被测系统。

### 为什么使用 Java？

营销中后台常见 Java/Spring 技术栈，而且它能和 Python 实现的 QualityPilot 形成真实的跨系统 HTTP 集成。选择 Java 也是为了让被测系统具备清晰的 Controller、Service、Repository 分层和可验证的数据库事务。

### 为什么不是微服务？

当前目标是验证 QualityPilot，不是模拟大型组织架构。模块化单体已经能表达客群和营销的责任边界，同时减少部署和联调成本。出现独立扩缩容、团队边界或数据隔离需求时，才有理由拆分服务。

### 现在最大的不足是什么？

当前只完成了客群链路，完整营销计划、审批、流程画布、频控、互斥、对照组、模拟触达和监控还没有实现，因此现在只能证明客群模块的业务和测试能力，不能声称已经完成完整 MDP 或 QualityPilot 端到端闭环。

### QualityPilot 在这里具体测试什么？

后续会输入 CampaignLab 的 PRD、业务规则、历史 Bug 和 OpenAPI，由 QualityPilot 识别需求缺失和冲突、分析风险、生成用例，经人工审核后调用 API，并结合响应和状态变化形成缺陷候选。CampaignLab 提供确定性结果，QualityPilot 的 AI 能力则接受独立评测。

## 第八步：迁移为前后端分离和 MySQL运行架构

- 状态：代码迁移和真实 MySQL运行验证均已完成。
- 前端：Vue 3 + TypeScript + Vite，端口 5173，独立安装和构建，通过 REST API访问后端。
- 后端：Spring Boot仅提供 `/api/**`，端口 8080，通过明确的 CORS白名单允许本地前端。
- 数据库：默认运行配置改为 MySQL 8.4；Flyway `V1`迁移建立客群、批次、成员、画像及遗留技术切片表。
- 测试隔离：Java测试显式启用 `test` profile并使用 H2 MySQL兼容模式，避免测试依赖本地数据库。
- 持久化纠正：正常应用启动只在画像表为空时装载合成画像，不再重置客群业务数据；测试重置仍由测试入口负责。
- 验证证据：Vue生产构建通过；12条Java测试通过；MySQL 8.4.11容器健康；Flyway V1成功；HTTP创建客群后可直接查询数据库，后端重启后数据仍存在。
- 验证中发现的问题：最初只引入Flyway核心库，Spring Boot 4没有加载自动配置，Hibernate先校验而报缺表；改为`spring-boot-starter-flyway`后迁移在JPA校验前成功执行。
- 当前边界：已经完成真实MySQL基础冒烟，但尚未补充MySQL并发、死锁、回滚和Testcontainers自动化测试。
- AI测试开发表达：我把H2限制在快速回归，同时为MySQL准备版本化Schema；下一步用真实MySQL/Testcontainers补足数据库兼容性证据。
- AI产品经理表达：架构升级不是为了堆技术，而是为了增加跨端契约、持久化、环境配置和真实事务等QualityPilot可测试风险。

## 第九步：重构客群管理信息架构并修复联调错误

- 状态：已完成列表、创建、详情三种视图的拆分和运行验证。
- 业务目标：用户进入 `客群圈选` 后先看到全部客群，再按任务进入创建或详情，避免左侧两个目录指向同一混合页面。
- 页面路径：左侧 `客群圈选` → 客群列表 → 创建客群或查看详情 → 预览、保存、发布、查看成员或触发动态计算。
- 设计选择：左侧只保留一个业务能力入口；创建和详情是页面状态，不重复成为一级目录。修改和删除因规则、状态限制和 API 尚未定义，明确标记为下一步能力，而不是放置无效按钮。
- 实际缺陷：后端 CORS 最初只允许 `localhost:5173`，用户实际通过 `127.0.0.1:5173` 访问时被拒绝；返回体还是纯文本，前端强制 JSON 解析后掩盖了真正原因。
- 修复：后端同时白名单放行两个本地源；前端根据 `Content-Type` 选择 JSON 或文本解析，保留原始错误信息。
- 验收证据：Vue 生产构建通过；12 条 Java 测试通过；前端和客群 API 均返回 200；`127.0.0.1:5173` 的 CORS 预检返回 200 和正确的 `Access-Control-Allow-Origin`；浏览器已检查列表、创建和详情视图。
- AI 测试开发面试表达：联调时我从用户可见的 JSON 解析异常追到真实的 CORS 配置差异，并分别修复服务端策略和客户端错误处理，再用预检请求、API、自动化测试和 UI 路径做分层回归。
- AI 产品经理面试表达：我根据任务频率重构后台导航，让列表承担管理入口、创建和详情承担具体任务，同时拒绝用不可操作的修改/删除按钮制造虚假完成度。
- 当前限制：列表搜索和筛选、修改规则生成 V2、删除或停用策略仍未实现，需在下一里程碑先明确业务规则。

## 第十步：建立 MDP 营销计划画布基础

- 状态：部分实现；数据模型、API、计划列表和顺序画布已完成，双分支画布编辑与执行引擎待实现。
- 业务模型：营销计划由节点和有向连线组成，节点类型包括开始、营销、判断、空白和延迟；画布是计划的创建方式，不是独立导航模块。
- 规则：草稿允许不完整；发布必须只有一个开始节点、所有节点可达、判断节点同时具有 YES/NO 分支，并且引用已发布客群版本。
- 数据库：Flyway V2 新增 `marketing_plan`、`flow_node`、`flow_edge`。
- 验证：前端构建通过，Java 测试从 12 条增加到 15 条，真实 MySQL V2 迁移成功，浏览器已检查营销计划列表和创建画布。
- 真实问题：H2 自动建表没有暴露 Hibernate 字段名与 MySQL Flyway 列名不一致；真实数据库启动校验发现后，通过显式 `@Column` 映射修复。
- 当前限制：页面只能顺序添加节点，尚不能可视化创建判断节点的 YES/NO 双分支；发布与执行监控的完整 UI 仍未完成。
- 后续纠正：画布已改为竖向；营销节点提供电话、短信、发券；判断节点提供 A/B、标签、回执并自动生成两条分支；新增结束节点和分钟延迟。发布校验新增 A+B=100、回执判断必须紧跟营销节点、延迟正整数、禁止循环及结束节点无出边。当前仍是受控组合器，不是自由拖拽画布，分支后的继续编排待下一步实现。
- UI 走查纠正：初版把两条分支边误渲染成两个纵向串行终点，虽然API数据正确，但视觉语义错误；现已按图关系过滤分支目标，并在判断节点下方并列绘制两条连线和各自终点。这说明图数据正确不等于用户看到的流程正确，UI结构也需要独立验收。
- 最终连接规则纠正：只有判断节点可分支；普通节点严格单出口。开始节点必须先进入 A/B 或标签判断；判断节点仅展示配置后的路径出口，不自动创建子节点；每条路径首节点由用户选择营销、空白或延迟，结束节点后续独立添加。空白/延迟可以连续出现，但属于允许而非推荐的低价值配置。
- 编辑能力补齐：画布改为递归渲染，普通节点下方可继续添加唯一下一节点直到结束；A/B 不再编辑内部 `AB:50:50` 字符串，而是配置 A 比例、自动计算 B，并把比例显示在对应路径标题上。

## 第十三步：建立 OpenAPI 合同与防漂移测试

- 状态：已完成 V1.0 当前接口合同；未包含任何 V1.1 计划能力。
