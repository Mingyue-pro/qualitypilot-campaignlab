# V1.1 PRD：用户日触达频控

## 1. 背景

同一个营销计划可能在一天内被多次启动，也可能在一条用户旅程中包含多个电话、短信或发券节点。如果执行引擎每次都直接调用渠道，同一用户会在短时间内收到过多营销触达，造成体验、成本和合规风险。

V1.1 增加计划级日触达上限：运营人员在创建计划时配置上限，执行引擎在每个营销节点调用渠道前，跨该计划当天所有执行批次统计用户已发生的渠道调用，并在达到上限时拦截。

## 2. 目标

- 运营人员能为每个营销计划配置每日触达上限。
- 执行引擎能跨运行批次正确统计同一计划、同一用户、同一上海自然日的渠道调用。
- 失败的渠道调用同样占用额度，避免失败重试造成过度触达。
- 被拦截行为能在用户执行轨迹中解释和审计。
- 测试人员能通过 API、轨迹和渠道回执交叉验证结果。

## 3. 非目标

V1.1 不包含：

- 跨营销计划的全局用户频控；
- 按电话、短信、发券分别配置渠道上限；
- 小时、周、月等多时间窗口；
- 用户级差异化额度；
- 频控豁免名单；
- 分布式缓存、Redis 原子计数或多实例并发方案；
- 延迟节点跨天自动恢复；
- 真实短信、外呼或发券渠道接入。

## 4. 用户故事

作为营销运营人员，我希望配置一个计划每天最多触达同一用户几次，从而避免计划重复执行或多营销节点导致过度触达。

作为测试人员，我希望看到被频控用户的明确节点轨迹，并确认被拦截时没有渠道回执，从而判断频控是否真正生效。

## 5. 功能需求

### FR-FC-001 配置日上限

创建营销计划时新增必填字段 `dailyContactLimit`：

- 类型：整数；
- 允许范围：1～5；
- 现有 V1.0 计划升级后的默认值：1；
- 草稿保存时校验类型和范围；
- 计划发布后该值随计划配置固定，V1.1 不支持编辑计划。

### FR-FC-002 触达前检查

执行到 `MARKETING` 节点时，必须在调用模拟渠道前统计：

```text
相同 plan_id
+ 相同 user_id
+ channel_receipt.created_at 属于当前 Asia/Shanghai 自然日
```

统计必须覆盖该计划当天以前的所有 `run_id`，也包括当前运行中更早的营销节点。

### FR-FC-003 计数事件

一次电话、短信或发券渠道请求实际发起后即占用一次额度：

- `SUCCESS` 计数；
- `FAILURE` 也计数；
- `FREQUENCY_CAPPED` 没有调用渠道，不计数。

`channel_receipt` 是当前版本判断“渠道请求已经发生”的事实证据。

### FR-FC-004 达到上限后的行为

当已用次数大于或等于 `dailyContactLimit`：

1. 不调用模拟渠道；
2. 不新增 `channel_receipt`；
3. 新增当前营销节点的 `node_execution`；
4. `node_execution.result` 为 `FREQUENCY_CAPPED`；
5. 如果下一节点是回执判断，则沿 `FAILURE` 路径继续；
6. 其他普通下游节点按原流程继续。

### FR-FC-005 自然日

时间窗口固定使用 `Asia/Shanghai`：

```text
当天 00:00:00（含）≤ created_at < 次日 00:00:00（不含）
```

不能使用服务器本地时区、UTC自然日或过去24小时替代上海自然日。

### FR-FC-006 监控展示

执行监控的逐用户轨迹需要显示：

- 被拦截的营销节点；
- 结果 `FREQUENCY_CAPPED`；
- 执行时间；
- 不展示不存在的渠道回执。

V1.1 不新增聚合频控报表。

## 6. 主流程

```text
执行到营销节点
→ 计算上海自然日边界
→ 统计计划+用户在当天所有运行批次的渠道回执
→ 已用次数 < 日上限：调用模拟渠道并保存回执
→ 已用次数 ≥ 日上限：不调用渠道，保存 FREQUENCY_CAPPED 轨迹
→ 继续后续流程
```

## 7. 权限

- 只有 `operator` 可以创建包含频控配置的营销计划。
- 查询计划和执行轨迹沿用 V1.0 的公开读取规则。
- V1.1 不新增角色。

## 8. 成功指标

- 所有验收场景具有确定性结果，可以重复运行；
- 被频控时新增渠道回执数为0；
- 同计划同用户同日的实际渠道调用不超过配置上限；
- 跨日、不同计划和不同用户不会被错误共享额度。
