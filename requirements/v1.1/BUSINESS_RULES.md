# V1.1 业务规则：用户日触达频控

| ID | 规则 | 违反时的预期结果 |
|---|---|---|
| `BR-FC-001` | `dailyContactLimit` 必填且必须为1～5的整数。 | 创建计划返回400，计划不落库 |
| `BR-FC-002` | 频控统计维度固定为 `plan_id + user_id + Asia/Shanghai自然日`。 | 不允许只按当前 `run_id` 统计 |
| `BR-FC-003` | 同一计划当天的所有执行批次共享额度。 | 后续批次达到上限时必须拦截 |
| `BR-FC-004` | 同一运行中的多个营销节点也共享额度。 | 后续节点达到上限时必须拦截 |
| `BR-FC-005` | 电话、短信、发券统一计入同一个计划级额度。 | 不按渠道分别重置额度 |
| `BR-FC-006` | 渠道请求一旦发起，`SUCCESS`和`FAILURE`均计数。 | 失败后重试不能绕过额度 |
| `BR-FC-007` | 被频控时不调用渠道、不写渠道回执。 | 只写 `FREQUENCY_CAPPED` 节点轨迹 |
| `BR-FC-008` | 被频控营销节点后的回执判断走 `FAILURE`。 | 不得沿 `SUCCESS` 路径 |
| `BR-FC-009` | 次日00:00:00（Asia/Shanghai）开始新额度。 | 前一日调用不计入次日 |
| `BR-FC-010` | 不同营销计划不共享额度。 | 计划A达到上限不阻止计划B |
| `BR-FC-011` | 不同用户不共享额度。 | U001达到上限不阻止U002 |
| `BR-FC-012` | 现有计划升级后使用默认上限1。 | 迁移后字段不得为空 |

## 术语

- **触达尝试**：执行引擎已经调用模拟渠道并生成一条 `channel_receipt`，不要求最终成功。
- **已用次数**：满足频控统计键和自然日范围的 `channel_receipt` 数量。
- **频控拦截**：执行引擎决定不调用渠道，并写入结果为 `FREQUENCY_CAPPED` 的节点轨迹。
- **自然日**：上海时区从当日00:00:00到次日00:00:00的左闭右开区间。

## 明确示例

计划P的上限为1。U001今天第一次短信调用返回`FAILURE`：

```text
已用次数 = 1
第二次执行 = FREQUENCY_CAPPED
第二次新增channel_receipt = 0
```

计划P和计划Q上限都为1。U001今天已经执行过P：

```text
再次执行P = FREQUENCY_CAPPED
第一次执行Q = 允许触达
```

## 冲突解释优先级

发生材料冲突时，优先级为：

1. 本需求包中已确认的 V1.1 规则；
2. 当前 V1.0 OpenAPI 与运行代码，用于判断既有事实；
3. 早期 V1.0 目标文档，仅作为历史背景。

不得因为早期文档曾出现“小时窗口频控”而把本需求解释为过去24小时或可配置小时窗口。
